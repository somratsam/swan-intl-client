### Brand logo filter — found live and fixed

Root cause was actually worse than "only works for transparent silhouettes": `brightness(0)` crushes every pixel to black regardless of source color, then `invert(1)` flips that to solid white — so it would blank out *any* image, including the seeded picsum placeholder "logos" that were never real logos to begin with.

Fixed:

- Listing-card badge (`BrandsPageClient.tsx`) sits over unpredictable photo content, so it got a radial dark scrim behind it (same technique as the D4 hero text scrim) for legibility, and switched from fixed `width`/`height` to `fill` mode in a sized `relative` box — this also fixed a `next/image` aspect-ratio console warning, caused by the global `img { height: auto }` rule (from Section A) fighting the explicit `height` prop.
- Hero logo (`brands/[id]/page.tsx`) was **removed entirely**, not just defiltered — the brand name already renders large right below it, so the logo was redundant there. The whole conditional block was deleted (not hidden), so the `justify-end` flex hero packs directly to the name with no leftover gap.
- Listing badge and admin table thumbnail were explicitly kept as-is (out of scope for the hero removal).

**Not yet fixed, flagged but out of scope for this pass:** `admin/brands/page.tsx`'s table thumbnail has its own `filter: 'invert(1)'` (not `brightness(0) invert(1)`) — now that real logos are white, this would invert them to black on a dark (`#1a1a1a`) table row background, i.e. invisible. ### Bulk Add (new feature — New Arrivals and Products both done)
New admin capability, separate from F1–F4: adding a whole delivery one record at a time was too slow. The existing single-record Add/Edit modal is untouched — Bulk Add is a second, create-only flow that sits alongside it.

- `src/lib/imageValidation.ts` — new shared module. Extracted the file-type/size constants and validators out of `ImageUpload.tsx` (which now imports from here) so bulk mode's validation can't drift from the single-upload component's — the login-token bug earlier this session was exactly this kind of "two places quietly disagree" problem, not worth repeating.
- `src/components/admin/BulkAddGrid.tsx` — new, generic, reusable component (not hardcoded to New Arrivals). Takes `columns: BulkColumn<T>[]` (each with `type: 'text'|'select'|'number'`, optional `required`) and a `createFn` injected by the caller — the upload mechanism itself (`useUploadImages`) is internal, not a prop, since there's only one upload path in this app.
  - Drop up to **25 images** (hard cap, enforced and stated in the dropzone text) — deliberately capped well below the backend's 10-per-request limit because 25 files × 5MB is real browser memory pressure on a machine that's already OOM-crashed twice this session; raise it later deliberately if 25 proves too low, rather than debugging a crash mid-delivery.
  - Uploads batch in groups of 10 (mirroring the backend's per-request cap). **On a batch failure, retries that batch file-by-file** rather than marking all ~10 rows failed — a single bad file failing a batch request would otherwise wrongly flag 9 good rows, and re-uploads across the whole batch would compound Cloudinary orphans (files that succeeded server-side before the batch request threw, now unlinked from any row). File-by-file retry only happens on the error path, so the happy path stays one request per chunk.
  - Row lifecycle tracks upload status and create status separately (`pending → uploading → uploaded → creating → success`, with `upload-failed`/`create-failed` branches) so a retry never repeats already-successful work — `success` rows are filtered out before anything else runs, structurally excluded from being re-created, not just skipped by convention.
  - Validates all required columns are filled *before* any network call — blocks the whole save and highlights incomplete rows rather than creating a partial batch from bad data.
  - Two-level progress: a phase banner ("Uploading images: X/Y" → "Creating records: X/Y") plus a per-row status badge.
  - `row.fields` is always `Record<keyof T, string>` at runtime regardless of a column's declared `type` (HTML inputs only return strings) — the grid now coerces `'number'` columns via a `buildPayload` step before calling `createFn`, so `createFn` always receives real numbers for numeric fields rather than every caller having to remember the conversion itself.
- **New Arrivals** (`admin/new-arrivals/page.tsx`): columns are `brand` (select, from `useBrands()`) and `caption` (text), both required. **Verified end-to-end by the user** at 8–10 photos — occasional first-image timeout on upload, retry saves it with no data loss, confirmed working at that scale.
- **Products** (`admin/products/page.tsx`): columns are `brand` (select), `name`, `category` (text), `price` (number), all required. Two gaps between the schema and those 4 columns, resolved by reading `product.validator.ts` directly rather than guessing:
  - `description` isn't a bulk column — auto-generated as `"${name} — details coming soon."`, since it's real public-facing body text but not worth slowing down rapid batch entry for; admin is expected to follow up via the single-record Edit modal.
  - `tags` (Zod requires `min(1)` — an empty array is rejected) defaults to `[brand]`.
  - `items[]` (Zod requires `min(1)` item; each item's `gallery` also requires `min(1)` — empty arrays rejected there too) gets one auto-generated item per row: `{ title: name, brand, image, description: <same placeholder>, gallery: [image] }`. ### Login token bug (found and fixed this session)
`swan_token` in localStorage was the literal string `"undefined"` — login appeared to succeed (`swan_user` saved correctly) but every authenticated request then sent `Bearer undefined` and got a 401, which surfaced as a generic "invalid or expired token" error with nothing actually expired. Root cause, verified by reading both ends directly:
- Backend (`auth.service.ts` + `auth.controller.ts`): login response is `{ success, message, data: { token, user } }` — the field is `token`.
- Frontend: `types/index.ts`'s `TAuthResponse` declared `data.accessToken` (wrong key), and `admin/login/page.tsx` read `res.data.accessToken` (always `undefined`) before calling `localStorage.setItem`.
- CLAUDE.md's own Auth Endpoints table also documented the wrong shape (`accessToken`) — that's almost certainly what the frontend was originally written against instead of the real API.

Fixed: `TAuthResponse.data.token` (renamed to match backend), `admin/login/page.tsx` now reads `res.data.token`, and a guard was added — if `token` is falsy, login is treated as failed (shown as an error) rather than storing `"undefined"`. CLAUDE.md's documented shape corrected too. **Verified by the user in the browser**: `swan_token` now stores a proper JWT.

### Section H — F4 completion: 401 handling, mobile nav logo, Cloudinary delivery helper (2026-07-28, done)

**1. 401 handling.** `api.ts` had a request interceptor but no response interceptor at all — confirmed broken per the 2026-07-27 report (an expired token left the admin UI rendering as if still logged in, with every subsequent call failing silently). Fixed:
- `api.ts`: added a response interceptor. On a `401` while on any `/admin/*` route other than `/admin/login`, it sets a `sessionStorage` flag (`swan_session_expired`) and dispatches a `window` event (`swan:unauthorized`) before rejecting the promise as normal. Gating on `pathname !== '/admin/login'` specifically excludes a failed login POST's own 401 (invalid credentials) from being treated as a session expiry — login attempts only happen from that one route.
- `AuthContext.tsx`: added a `useEffect` that listens for `swan:unauthorized` and calls the existing `logoutFn()` (clears `swan_token`/`swan_user`, resets state). No new logout path — reuses the one already wired to the manual Logout button.
- `AdminLayoutClient.tsx` — **untouched**. Its existing guard effect (`if (!user || !isAdmin) router.replace('/admin/login')`) already fires correctly once `AuthContext` clears `user`, so the redirect falls out of the existing code for free.

### Section I — Password reset flow, auth-loading-flash fix (2026-07-28, done, browser-verified)

**1. Password reset — backend (`swan-intl-m-server`)**
- `user.model.ts`/`user.interface.ts`: added `resetPasswordToken`/`resetPasswordExpires`, both `select: false` (same treatment as `password` — never returned by a normal query, no manual scrubbing needed).
- `auth.interface.ts`/`auth.validator.ts`: `TForgotPasswordPayload`/`TResetPasswordPayload`; `ForgotPasswordValidator` (email only); `ResetPasswordValidator` (token + password, reusing `RegisterValidator`'s exact `min(6)` password rule/message rather than inventing a stricter one).
- `auth.service.ts`: `forgotPassword` — `crypto.randomBytes(32)` raw token, sha256-hashed before storing (raw token never persisted), 1-hour expiry (hardcoded constant, not env-configurable), silent no-op if no matching user. The enumeration-prevention guarantee lives here, in the service, not just in the controller's response wording. `resetPassword` — hash-and-match lookup; `user.password = payload.password; await user.save()` rather than hand-rolling `bcrypt.hash`, so the existing `pre('save')` hook does the hashing exactly as it does for every other password write in this codebase.
- `auth.controller.ts`: `resetPassword` follows the existing register/login error-mapping pattern. `forgotPassword` is **deliberately different** — it returns the identical `200` generic message to the client even on a genuine downstream failure (Resend down, DB hiccup), logging the real error server-side via `console.error` instead. Reasoning: if failures produced a different response than successes, that response-shape difference would itself be a timing/enumeration side channel, so the "always the same message" guarantee has to hold even when something breaks, not just on the happy path.
- `auth.route.ts`: new `forgotPasswordLimiter` — 3 requests/hour, keyed by email (falling back to IP via `express-rate-limit`'s `ipKeyGenerator` helper for malformed/missing email) — layered on top of the existing IP-based `authLimiter` (5/15min) that `app.ts` already mounts on the whole `/api/auth` prefix. Covers both the "per email" and "per IP" abuse vectors asked for; `reset-password` relies on the inherited IP limiter alone since brute-forcing a 256-bit random token isn't something a dedicated limiter meaningfully adds protection against.
- **Explicitly out of scope, by design, not an oversight:** no self-service role-change or admin-creation UI. That stays a manual Atlas edit specifically to avoid reopening the privilege-escalation surface closed in backend commit `b33ec93`.

**2. Password reset — email delivery, `src/app/utils/email.ts` (new file, backend)**
Real debugging chain, not a first-try success — the root causes are reusable knowledge, also captured in `CLAUDE.md` rules 15–16:
1. Started with the `resend` npm SDK — its `ResendOptions` only exposes `baseUrl`/`userAgent`, no hook for a custom timeout or dispatcher.
2. Node's global `fetch` (undici) has a hardcoded 10s connect timeout; this machine's real handshake latency to `api.resend.com` measured ~22.7s (a raw Node `fetch` test failed at exactly undici's 10s ceiling, while a PowerShell `Invoke-WebRequest` succeeded at ~22.7s). Freeing RAM (from ~350MB to ~1.15GB free) did **not** fix this — a genuinely different root cause from the earlier documented memory-pressure incident, despite an identical first symptom.
3. Switched to calling Resend's REST API directly via the standalone `undici` package's own `fetch` + a dedicated `Agent({ connectTimeout: 30000 })` passed as `dispatcher`, scoped to just this one call — not a global fetch/dispatcher change. First attempt passed that external `Agent` into Node's *global* `fetch` and broke (`UND_ERR_INVALID_ARG`, "invalid onRequestStart method") — Node's internally bundled undici and the external npm `undici` package aren't wire-compatible for the dispatcher handler interface. Fixed by importing `fetch` from the `undici` package too, so `Agent`/`dispatcher`/`fetch` all come from one self-consistent implementation. The `resend` package was uninstalled once it was no longer used for anything.
4. The `sendPasswordResetEmail(...)` call in `auth.service.ts`'s `forgotPassword` is deliberately **not awaited** — fire-and-forget with a `.catch()` that logs — so a slow or failed send can never block the `POST /forgot-password` response. Verified: response latency dropped from 10s+/timeout to a flat ~0.2s regardless of the email outcome.
5. A real Resend `403` followed once the connection itself worked: free-tier test mode only sends to the account's own verified address, registered as `it.department@swan-intl.com` (lowercase), while the DB stores `IT.Department@swan-intl.com` (mixed case) — Resend's allowlist check is case-sensitive. Fixed by lowercasing specifically at the point of calling Resend (`user.email.toLowerCase()`), without touching the DB lookup (which already matches correctly on whatever casing is typed) or any other auth flow.
- **Template redesign:** originally a plain heading/paragraph/button. Redesigned on request — table-based layout (`role="presentation"`), inline styles only, `bgcolor` HTML attributes doubled up with CSS `background-color` for Outlook, a "bulletproof button" pattern (colored table cell, not a styled bare `<a>`). Aubergine (`#4A2545`) header band with a serif (Georgia/Times New Roman fallback stack — no web fonts; Outlook desktop has zero `@font-face` support) two-line "SWAN / INTERNATIONAL" wordmark matching the site's own hierarchy (same cream color for both lines, distinguished by size/tracking, not dimmed — matches `Navbar.tsx`'s actual treatment). Mauve (`#8B6F8C`) border + accent strip. White body for legibility, brand color deliberately concentrated in header/border/button rather than tinting the reading area. Expiry note and the "if you didn't request this" disclaimer split into visually distinct sections — same exact wording preserved throughout, only the visual grouping changed. Design was rendered and reviewed as a published Artifact (the real HTML in an isolated iframe, not a description of it) before being applied to `email.ts`.
- **Verified end-to-end in a real inbox, twice** — once against the original plain template, again after the redesign — by the user checking `it.department@swan-intl.com` directly and confirming correct rendering, not just a `200` response from the API.

**3. Password reset — frontend (`swan-intl-client`)**
- `api.ts`/`useApi.ts`: `forgotPassword`/`resetPassword` calls and `useForgotPassword`/`useResetPassword` mutation hooks, mirroring the existing `login`/`useUploadImages` shapes exactly.
- `AdminLayoutClient.tsx`: the single `isLoginPage` check widened to a `PUBLIC_ADMIN_PATHS` allowlist (`/admin/login`, `/admin/forgot-password`, `/admin/reset-password`). - `admin/login/page.tsx`: "Forgot password?" link added under the password field.
- New `admin/forgot-password/page.tsx`: same shell as login (centered card, brand header). Zod/network errors → error Toast, form stays open, input correctable. A real `200` (regardless of whether the account existed) → success Toast **and** the form is replaced by a persistent "Check Your Inbox" panel — a 3.5s auto-dismissing toast alone isn't enough signal for a message this consequential.

- Verified: `npx tsc --noEmit` clean, `npm run build` 26/26 routes (two new). **4. Auth-loading-flash bug — found and fixed**
User-reported: reloading any admin page briefly flashed the login page before the real admin content appeared. Root cause, confirmed by reading the code rather than assumed:
- `AuthContext.tsx` had no `isLoading`/`isInitialized` state. `user` starts `null` on every mount and is only populated inside a `useEffect` that reads `localStorage` — which runs *after* the first commit, not during it. `user === null` was structurally ambiguous between "haven't checked yet" and "checked, no session."
- `AdminLayoutClient.tsx`'s guard effect treated both cases identically: `if (!isPublicPage && (!user || !isAdmin)) router.replace('/admin/login')` fired on the very first, still-unresolved render.
- Because `AuthProvider` wraps the tree from the root `layout.tsx` and `AdminLayoutClient` is a descendant of it, and React fires effects bottom-up within a commit (children before parents), `AdminLayoutClient`'s guard effect actually ran *before* `AuthProvider`'s own localStorage-reading effect in the same pass — so the redirect to `/admin/login` was a real client-side navigation fired on stale data, not a rendering artifact. The login page's own "already logged in, redirect to dashboard" effect then caught the freshly-resolved `user` a moment later and bounced back — two real navigations landing within about a frame, reading as one flash.
- **Fix:** added `isLoading: boolean` to `AuthContextType`, `true` until the localStorage-read effect finishes (set to `false` unconditionally at the end of that effect, regardless of which branch — found+valid, found+corrupt, or not found — it took). `AdminLayoutClient.tsx`'s guard now waits for `!isLoading` before redirecting, and its render logic shows the spinner while `isLoading || !user || !isAdmin` (previously just the latter two). Also found and fixed the **identical** pattern in a third file, `admin/page.tsx` (the bare `/admin` route) — it had its own independent redirect effect with an unconditional `else { router.replace('/admin/login') }`, found by grepping every `useAuth()` consumer in the codebase rather than stopping at the two files originally named. `Navbar.tsx` and `admin/login/page.tsx` were checked too and needed no changes — both only act on the *positive* `user && isAdmin` signal, never on `!user`, so neither was susceptible to this race.
- Verified: `tsc`/build clean, 26/26 routes. **Confirmed by the user in the browser** — no more flash on any admin page, including bare `/admin`.

- Notification email is HTML-escaped on all four visitor-supplied fields (`escapeHtml()`) before interpolation — a submission containing `<script>`/`&`/`"` etc. would otherwise inject arbitrary markup into the internal notification email. Verified directly: submitted a payload containing those characters, confirmed the DB stores the raw text (escaping is a presentation-layer concern, not a storage-layer one) while the email-building code path escapes it.
- Frontend: `ContactPageContent.tsx`'s `handleSubmit` now calls the real endpoint via a new `useSubmitContactForm()` hook. **Real correctness fix, not cosmetic:** the old version cleared the form unconditionally, which was harmless when nothing could actually fail — now that failure is possible, the form only clears on a confirmed success, so a real failure no longer silently destroys what the visitor typed.

Fixed the same way — lowercase the constant.
- Verified: real submission → `201` + real DB row; missing/invalid fields → `400` with real Zod messages; unauthenticated `GET` → `401`; rate limiter actually blocks the 6th submission/hour (`429`, correct message). **Confirmed working end-to-end by the user in the browser**, including the real notification email arriving.

**2. Resend domain verification (`swan-intl-m-server`)**
- `updates.swan-intl.com` verified in Resend. `RESEND_FROM_EMAIL` updated (`config/index.ts`'s fallback, `.env`, `.env.example`) from the `onboarding@resend.dev` sandbox address to `Swan International <no-reply@updates.swan-intl.com>`.

**3. Admin Messages/reply (`swan-intl-m-server` + `swan-intl-client`)**
- `contact` module extended: `replyText`/`repliedAt` (both optional) added to the schema/interface; `ReplyValidator` added as a **named** export alongside the existing default-exported `ContactValidator` (mirrors `auth.validator.ts`'s precedent for a module needing more than one validator, without restructuring the existing import in `contact.controller.ts`); `contact.service.ts` gains `getSingleContactFromDb`, `markContactAsRead`, `addReplyToContact`; `getAllContactsFromDb` gains basic `page`/`limit` support (the "add pagination... if not already present" ask — sorting newest-first already existed). New routes `PATCH /api/contact/:id/read` and `POST /api/contact/:id/reply`, both `authMiddleware, adminOnly`.
- **`replyToContact` is the one place in this codebase that deliberately does *not* use the fire-and-forget email pattern, and it's worth remembering why if this comes up again:** `forgotPassword`/`createContact`'s notification emails are side effects of an action that already succeeded independently (a token was issued; a message was saved) — hiding a downstream email failure there is *correct*, because the thing the user cares about already happened. Here, sending the email **is** the entire point of the endpoint. `sendContactReply(...)` is **awaited**; a failure surfaces as a real `502` with the underlying message, so the admin knows synchronously that a reply didn't actually go out. Reply history is a single `replyText`/`repliedAt` pair, not a thread — once a reply exists, the UI shows it read-only rather than offering a second send that would silently overwrite the first with no record of it (a real gap in the data model, flagged rather than quietly worked around).

Test data cleaned up carefully — two real submissions the user had already sent through their own browser test were identified and deliberately left untouched. **Confirmed working end-to-end by the user in the browser**: list, unread/read state, reply sending and receiving, and persistence after reload.
